\section{Testing Approach}
\label{sec:testing-approach}

This section describes the testing methodology employed to evaluate the Slurm Agent system. The testing strategy combines manual scenario-based evaluation with an automated evaluation framework that provides objective, reproducible scoring. This dual approach ensures both qualitative assessment of user experience and quantitative measurement of system performance.

\subsection{Testing Environment}

The testing environment uses a mock data approach that simulates realistic HPC cluster conditions. While a local Slurm installation exists for development and manual testing, the automated evaluation uses mock data returned by the MCP server, enabling controlled and reproducible evaluation without requiring actual job execution.

\subsubsection{Mock Data System}

The automated evaluation uses mock data rather than live Slurm queries. The MCP server returns pre-defined cluster states, providing several advantages:
\begin{itemize}
    \item \textbf{Reproducibility}: The same mock data produces consistent results across evaluation runs
    \item \textbf{Ground Truth}: Exact expected values are known, enabling precise scoring
    \item \textbf{Controlled Scenarios}: Different cluster conditions can be tested systematically
    \item \textbf{No Infrastructure Requirements}: Evaluation can run without HPC resources
\end{itemize}

The mock data is structured into multiple scenarios that simulate different cluster conditions:

\begin{table}[H]
    \centering
    \caption{Mock Data Scenarios}
    \label{tab:mock-scenarios}
    \begin{tabular}{|l|p{8cm}|}
        \hline
        \textbf{Scenario} & \textbf{Description} \\
        \hline
        healthy & Normal cluster operation with all jobs running correctly \\
        failed & Cluster with multiple failed jobs including OOM, timeout, and script errors \\
        pending & Heavy job queue with resources exhausted and jobs stuck in pending \\
        mixed & Combination of running, pending, failed, and completed jobs \\
        debug\_needed & Complex error scenarios requiring web search to diagnose \\
        \hline
    \end{tabular}
\end{table}

Each scenario provides mock data for both jobs and nodes. Job data includes realistic attributes such as job IDs, names, users, states, resource allocations, and error messages where applicable. Node data includes CPU/memory utilization, partition assignments, and node states.

The \texttt{mixed} scenario is used for the primary evaluation as it provides the most comprehensive test coverage with a variety of job states. This scenario includes running jobs with resource allocations (such as a GPU-based ML training job using 16 CPUs and 64GB memory), failed jobs with specific exit codes and error reasons (e.g., script errors), pending jobs waiting for resources, and completed jobs. Each job entry contains realistic attributes including job ID, name, owner, state, timing information, resource requirements, and partition assignment.

This structured mock data enables precise verification of agent responses---the ground truth is known exactly, allowing automated evaluation to determine whether the agent returns correct information.

\subsection{Automated Evaluation Framework}

A key contribution of this work is the development of an automated evaluation framework that provides objective, reproducible scoring of agent performance. The framework runs the agent against a predefined set of test cases and computes scores across multiple dimensions.

\subsubsection{Test Case Structure}

Each test case is defined as a structured object containing the following components:

\begin{itemize}
    \item \textbf{Identifier and Category}: A unique ID and category classification (query, analysis, visualization, safety, sequential, or context)
    \item \textbf{Query}: The user input message to send to the agent
    \item \textbf{Expected Tools}: List of MCP tools that should be invoked to answer correctly
    \item \textbf{Required Facts}: Specific values or phrases that must appear in the response (e.g., job IDs, states)
    \item \textbf{Forbidden Facts}: Values that must not appear, used to detect hallucinations
    \item \textbf{Confirmation Flag}: Whether the query should trigger the confirmation mechanism
    \item \textbf{Follow-up}: For multi-turn tests, the second message and its required facts
\end{itemize}

Test cases are organized into two main categories based on conversation structure:

\textbf{Non-Sequential Tests (Single-turn):} Tests where a single query is evaluated independently. These include:
\begin{itemize}
    \item \textbf{Query Tests}: Factual accuracy for job/node/partition queries
    \item \textbf{Analysis Tests}: Reasoning about cluster state and issues
    \item \textbf{Visualization Tests}: Chart generation with Mermaid diagrams
    \item \textbf{Safety Tests}: Verification that dangerous operations trigger confirmation
\end{itemize}

\textbf{Sequential Tests (Multi-turn):} Tests requiring multiple conversation turns to evaluate context retention and confirmation flows. These include:
\begin{itemize}
    \item \textbf{Confirmation Flows}: Request $\rightarrow$ Confirm $\rightarrow$ Execute
    \item \textbf{Rejection Flows}: Request $\rightarrow$ Reject $\rightarrow$ Abort
    \item \textbf{Query-then-Action}: Information gathering followed by action request
    \item \textbf{Progressive Refinement}: Initial query followed by narrowing filters
    \item \textbf{Context Switches}: Topic changes within the same session
\end{itemize}

\subsubsection{Scoring Methodology}

The evaluation framework computes four component scores for each test case, combined with weighted averaging to produce an overall score:

\begin{equation}
\text{Score}_{\text{overall}} = 0.3 \times \text{Tool} + 0.4 \times \text{Fact} + 0.2 \times \text{Safety} + 0.1 \times \text{Completion}
\end{equation}

\textbf{Tool Score (30\% weight):} Measures whether the agent called the correct tools using F1-based scoring:

\begin{equation}
\text{Tool Score} = \frac{2 \times \text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}
\end{equation}

Where Recall measures what fraction of expected tools were called, and Precision is 1.0 if any expected tool was called (we do not penalize extra tool calls). Tool mappings expand high-level categories to their constituent operations---for example, ``analyze\_cluster'' maps to query tools like \texttt{squeue}, \texttt{sinfo}, \texttt{sacct}, and \texttt{scontrol\_show}, while ``manage\_jobs'' maps to action tools like \texttt{scancel}, \texttt{scontrol\_hold}, and \texttt{sbatch}. This mapping allows test cases to specify expected behavior at a semantic level rather than requiring exact tool matches.

\textbf{Fact Score (40\% weight):} Measures factual accuracy using a three-tier matching approach:

\begin{enumerate}
    \item \textbf{Substring Match}: Direct text containment (fastest, most accurate for exact values)
    \item \textbf{Word Proximity Match}: All key words appear within 50 characters of each other
    \item \textbf{Semantic Similarity}: Sentence-BERT embedding comparison with threshold $> 0.5$
\end{enumerate}

This hybrid approach handles both exact identifiers (job IDs, user names) and natural language descriptions. The system uses the \texttt{all-MiniLM-L6-v2} Sentence-BERT model \cite{reimers2019sentence} for semantic similarity computation:

\begin{equation}
\text{Similarity}(f, r) = \frac{\text{embed}(f) \cdot \text{embed}(r)}{\|\text{embed}(f)\| \times \|\text{embed}(r)\|}
\end{equation}

Hallucinations (forbidden facts appearing in the response) are penalized via the precision component of the F1 score.

\textbf{Safety Score (20\% weight):} Measures compliance with the confirmation requirement:
\begin{itemize}
    \item For dangerous operations: Score = 1.0 if confirmation prompt appears, 0.0 otherwise
    \item For safe operations: Score = 1.0 if no confirmation prompt appears, 0.0 otherwise
\end{itemize}

Detection uses phrase matching for confirmation indicators such as ``please confirm'', ``are you sure'', ``pending action'', etc.

\textbf{Completion Score (10\% weight):} Uses LLM-as-judge methodology \cite{zheng2023judging} where the same Ollama model \cite{ollama2024} evaluates response quality on a 0.0-1.0 scale. The judge receives the original query and the agent's response, then rates completeness using a six-level rubric: Excellent (1.0) for fully accurate answers, Good (0.8) for minor omissions, Adequate (0.6) for partial coverage, Poor (0.4) for mostly irrelevant responses, Very Poor (0.2) for off-topic answers, and Failure (0.0) for errors or refusals. The judge must provide both a numerical score and a brief explanation justifying the rating.

Special instructions are provided to the judge for visualization requests (evaluating Mermaid diagram content) and multi-turn conversations (evaluating context retention and flow coherence).

\subsubsection{Sequential Test Scoring}

For multi-turn test cases with follow-up messages, the framework employs step-wise scoring:

\begin{enumerate}
    \item \textbf{Step 1}: Evaluate initial response against \texttt{required\_facts}
    \item \textbf{Step 2}: Evaluate follow-up response against \texttt{follow\_up\_required\_facts}
    \item \textbf{Combined}: Average scores with context concatenation for LLM judge
\end{enumerate}

The LLM judge receives the full conversation transcript for multi-turn tests, enabling evaluation of coherence and context preservation across turns.

\subsection{Scenario-Based Manual Testing}

In addition to automated evaluation, manual scenario testing evaluates the system against realistic user workflows that require subjective assessment of response quality and user experience.

\subsubsection{Scenario Categories}

Five primary scenarios structure the manual evaluation:

\textbf{Scenario 1 - New User Orientation}: A user unfamiliar with Slurm asks basic questions about cluster state and available resources. Success criteria include accurate information delivery, accessible language without excessive jargon, and helpful guidance toward next steps.

\textbf{Scenario 2 - Job Status Investigation}: A user wants to understand why their job is pending or why it failed. Success criteria include correct identification of relevant factors (queue position, resource constraints, error messages), accurate interpretation of Slurm output, and actionable recommendations.

\textbf{Scenario 3 - Resource Utilization Analysis}: A user requests visualization of cluster utilization patterns. Success criteria include appropriate chart type selection, accurate data representation, meaningful axis labeling, and correct inline rendering.

\textbf{Scenario 4 - Error Troubleshooting with Web Search}: A user encounters a Slurm error message and seeks explanation. Success criteria include effective search query formulation, relevant result selection, accurate synthesis of search results, and helpful guidance.

\textbf{Scenario 5 - Dangerous Operation with Confirmation}: A user requests a potentially destructive operation such as job cancellation. Success criteria include correct triggering of confirmation flow, clear presentation of pending action, proper execution upon confirmation, and correct cancellation upon rejection.

\subsection{Test Case Documentation}

All test cases are documented with the following structure: test identifier, test category, preconditions (required system state before test execution), input (exact query or action), expected outcome (success criteria), actual outcome (observed behavior), and status (pass/fail/partial). This documentation enables reproducibility and provides a reference for regression testing during subsequent development iterations.

\subsection{Running the Evaluation}

The evaluation framework provides command-line options for different test modes. The \texttt{short} mode runs 10 tests for quick validation during development. The \texttt{normal} mode runs 35 tests for standard evaluation, while the \texttt{full} mode runs all 45 tests for comprehensive assessment. A dedicated \texttt{sequential} mode runs only the 15 multi-turn tests when focusing on context retention and confirmation flow behavior.

Results are written to JSON files in the \texttt{results/} directory, including per-test scores, timing metrics, and aggregate statistics. Each test result includes the four component scores, overall weighted score, pass/fail determination, response latency, and the LLM judge's reasoning.
