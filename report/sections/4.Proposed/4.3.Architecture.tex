\section{System Architecture}
\label{sec:architecture}

This section presents the overall architecture of the Slurm Agent system, describing the major components, their interactions, and the rationale behind architectural decisions. The design uses common web and agent frameworks, but the architectural contribution is the Slurm-specific control plane built on top of them: broad Slurm tool coverage, read/write separation with confirmation, and local documentation grounding.

\subsection{Architecture Overview}

The Slurm Agent is organized as a four-layer stack. At the top, a thin \textbf{Interface Layer} accepts natural-language requests and relays confirmation decisions without embedding any domain logic. Below it, the \textbf{Agent Layer} houses the Observer/Operator multi-agent backend that performs ReAct reasoning, retrieves documentation, and enforces safety routing—the Observer handles read-only inspection and decides when to hand off to the Operator for state-changing operations. The \textbf{Protocol Layer} exposes each Slurm operation as a typed MCP tool with parameter validation, isolating the agent from raw command-line construction. At the bottom, the \textbf{Infrastructure Layer} provides the actual execution targets—either a live Slurm cluster or a mock scenario engine—alongside the local documentation corpus and external services.

This separation ensures that the boundary between reading cluster state and mutating it is an explicit architectural seam rather than an implicit convention. Read-only inspection flows entirely within the Observer path, while any state-changing operation must cross into the Operator path and pass through a confirmation gate before reaching the MCP tool layer.

\subsection{Design Rationale}

The main design decision is to treat Slurm interaction as a controlled operation surface rather than as open-ended command generation. A general chatbot can explain commands, but a cluster assistant must also decide when to inspect live state, when to consult documentation, when to ask for clarification, and when to refuse or delay execution until a user confirms intent. The architecture therefore combines two forms of grounding:

\begin{itemize}
    \item \textbf{Operational grounding}: current cluster facts come from Slurm tools exposed through MCP.
    \item \textbf{Documentation grounding}: command syntax, reason-code meanings, and policy-like explanations come from local Slurm documentation retrieval.
\end{itemize}

The architecture is also designed to support incomplete or ambiguous user requests. When the user says a phrase such as ``cancel that job'', the system must determine whether a specific job is already known from context. If the target is unclear, the safe behavior is to ask for clarification. If the target is clear but the action changes cluster state, the safe behavior is to create a pending action and require confirmation. This is why session state and pending-action persistence are architectural components rather than UI conveniences.

\subsection{Component Descriptions}

\subsubsection{Interface Layer}

The Interface Layer is intentionally thin. It provides an entry point for manual prompts, automated evaluation prompts, and explicit confirmation decisions. This layer is responsible for:

\begin{itemize}
    \item forwarding natural-language requests to the agent backend,
    \item presenting final responses and selected status events,
    \item relaying confirm/cancel decisions for pending actions,
    \item exposing traces needed for debugging and evaluation.
\end{itemize}

The interface is therefore support infrastructure, not the central contribution. Agent behavior is defined by the backend control flow and can be exercised either manually or through the automated evaluator.

\subsubsection{Agent Layer}

The Agent Layer implements core reasoning and orchestration using a dual-agent architecture. Both agents share the same fine-tuned LLM and MCP tool connection but operate under distinct system prompts and tool-access policies:

\begin{itemize}
    \item \textbf{Observer}: The primary entry point for every request. It implements the ReAct reasoning loop (Think $\rightarrow$ Act $\rightarrow$ Observe), classifies user intent, and handles all read-only operations---queue inspection, node status, accounting queries, reservation checks, scheduler diagnostics, documentation retrieval, and web search. When the request requires cluster state modification, the Observer produces a structured handoff directive specifying the action, target scope, and tool, then delegates to the Operator.
    
    \item \textbf{Operator}: Receives handoff directives for state-changing operations such as job submission, cancellation, hold, release, requeue, and configuration updates. It may perform a single discovery read to resolve targets (e.g., listing jobs before cancelling), then invokes the action tool. Execution is gated by a human-in-the-loop confirmation step for all destructive operations.
\end{itemize}

This division is central because incorrect execution can waste compute time, interrupt other users, or change shared cluster policy. The Observer never holds action tools, and the Operator never runs without an explicit handoff---ensuring that the boundary between reading and mutating state is enforced by the framework rather than by prompt compliance alone.

Beyond safety enforcement, the dual-agent design provides a measurable \textbf{tool-scope reduction} benefit for capacity-constrained local models. The full Slurm tool surface comprises 18 distinct tools; presenting all of them simultaneously to a 14B-parameter model degrades tool-selection accuracy as the model's attention must discriminate among semantically similar options (e.g., \texttt{sacct} vs.\ \texttt{squeue} vs.\ \texttt{sacctmgr\_list}). By partitioning tools into two focused subsets of approximately 8 tools each, each agent operates within a smaller selection space where correct tool identification is easier. Ablation experiments in Section~\ref{sec:ablation} quantify this effect.

\subsubsection{Protocol Layer}

The MCP Protocol Layer wraps each Slurm command as a typed tool with parameter validation, operational semantics preservation, safe subprocess execution, and structured output formatting. It decouples agent logic from Slurm implementation details and provides a security boundary for command execution.

\subsubsection{Infrastructure Layer}

The Infrastructure Layer provides external execution targets and supporting services. It includes: (1)~the LLM provider (local Ollama, self-hosted fine-tuned model via OpenAI-compatible endpoint, or cloud API), (2)~the Slurm cluster itself (real CLI access or mock scenario engine for evaluation), (3)~a local documentation corpus indexed for retrieval, (4)~a web search service for fallback queries, and (5)~a SQLite context database for session persistence.

\subsection{Communication Patterns}

The system uses four communication patterns: (1)~request-response for simple queries where the agent returns a single grounded answer, (2)~structured event streaming (SSE) for real-time status updates, tool-call progress, and reasoning trace events, (3)~tool invocation via MCP where the agent sends typed requests with validated parameters and receives structured JSON responses, and (4)~confirmation interruption where the event stream pauses mid-execution to present pending actions and await user approval before resuming.


\subsection{Data Flow}

A typical query flows: (1)~user submits request, (2)~Agent Layer begins ReAct reasoning, (3)~delegates to Observer or Operator, (4)~sub-agent invokes MCP tools, (5)~results propagate back, (6)~agent synthesizes response with trace events. For dangerous operations, an additional confirmation step interrupts the flow before execution.

\subsection{Deployment Architecture}

The system supports local development (all components on one machine) and distributed deployment (interface, backend, and MCP server on separate hosts, with MCP on a Slurm management node).
