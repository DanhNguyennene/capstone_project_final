\section{Agent Backend Implementation}
\label{sec:agent-backend}

The backend maintains session-aware multi-agent execution, exposes an OpenAI-compatible chat API, and enforces confirmation workflows for state-changing operations.

\subsection{Technology Stack}

\begin{itemize}
    \item \textbf{FastAPI + Uvicorn}: API layer for chat, health, and session endpoints
    \item \textbf{OpenAI Agents SDK}: multi-agent orchestration and tool-driven execution
    \item \textbf{MCP over SSE}: tool discovery and execution against the Slurm MCP server
    \item \textbf{SQLiteSession}: persistent per-session context and chat history
\end{itemize}

Model routing supports local Ollama (default) and optional remote providers.

\subsection{Agent Topology}

The system implements a two-agent architecture with bidirectional handoffs:

\begin{itemize}
    \item \textbf{Observer}: the primary orchestrator and entry point for all requests. It handles read-only inspection (queue status, node info, accounting, diagnostics), documentation retrieval, and intent classification. When a state-changing action is identified, the Observer hands off to the Operator with a structured payload specifying the required tool, targets, and action description.
    \item \textbf{Operator}: a restricted execution agent that receives structured handoffs from the Observer. It may perform one discovery read to resolve ambiguous targets (e.g., resolving ``that job'' to a job ID), then executes the confirmed action. After completion, it hands back to the Observer.
\end{itemize}

Both agents share the same underlying LLM but operate with different tool sets, system prompts, and model settings (the Observer uses \texttt{tool\_choice=auto}; the Operator uses \texttt{tool\_choice=required}). The Observer's MCP tool surface is limited to read-only Slurm commands, while the Operator receives both dangerous action tools and a subset of read tools for target resolution.

Additional utility tools available to the Observer: \texttt{generate\_chart}, \texttt{lookup\_slurm\_docs}, and \texttt{lookup\_skill}. Confirmation tools (\texttt{confirm\_action}, \texttt{cancel\_action}, \texttt{check\_pending\_actions}) are implemented as guarded wrappers that enforce human approval before the underlying MCP tool executes.

\subsection{Safety and Confirmation Pipeline}

Dangerous operations follow a queued-action workflow: (1)~the request is transformed into a pending action (not executed), (2)~the user sees the action and must explicitly confirm, (3)~execution occurs only via \texttt{confirm\_action}. This two-step control reduces accidental cluster mutations.

\subsection{Hybrid RAG Documentation Retrieval}
\label{sec:impl-rag}

The agent includes a local retrieval tool (\texttt{lookup\_slurm\_docs}) that provides Retrieval-Augmented Generation over the official Slurm documentation corpus. The pipeline operates without an external vector database---all indexing is in-memory.

\subsubsection{Corpus Preparation}

A crawl script fetches all HTML pages from \texttt{slurm.schedmd.com}, converts them to Markdown with YAML frontmatter (source URL, title, fetch timestamp), and stores them in a local corpus directory. At the time of writing the corpus contains 273~documents covering commands, configuration, accounting, scheduling, and troubleshooting.

\subsubsection{Chunking Strategy}

Each document is split at heading boundaries (\texttt{\#}, \texttt{\#\#}, \texttt{\#\#\#}). Chunks smaller than 80~characters are discarded; chunks exceeding 1{,}400~characters are further split at paragraph boundaries. This produces 2{,}276 chunks with an average length of approximately 600~characters, balancing retrieval granularity against context window cost.

\subsubsection{Dual Retrieval}

At query time, the tool runs two parallel scoring passes:

\begin{enumerate}
    \item \textbf{Lexical scoring}: token-overlap BM25-style matching between the normalized query and chunk content, with bonuses for phrase matches and path/title matches.
    \item \textbf{Semantic scoring}: the query is encoded using the all-MiniLM-L6-v2 sentence-transformer model~\cite{reimers2019sentence} (384-dimensional embeddings, running on GPU). Cosine similarity against pre-computed chunk embeddings identifies semantically related passages.
\end{enumerate}

\subsubsection{Reciprocal Rank Fusion}

The two ranked lists are fused using RRF with $k=60$~\cite{cormack2009reciprocal}. The top-5 results are returned as context snippets (each capped at 950~characters), yielding approximately 1{,}200~tokens per tool call---a small fraction of the model's context window.

\subsubsection{Pre-computed Embeddings}

To avoid a GPU-intensive embedding pass at server startup, a build script (\texttt{build\_embeddings.py}) pre-computes all 2{,}276 chunk embeddings and saves them as a compressed NumPy archive (\texttt{embeddings.npz}, 3.2~MB). At runtime the agent loads this file in under 100~ms. If the corpus is updated and the embedding count diverges, the system falls back to runtime embedding.

\subsubsection{Design Rationale}

This hybrid approach addresses a practical limitation observed during evaluation: purely lexical retrieval fails on paraphrased queries (e.g., ``how to chain jobs'' does not lexically match ``dependency afterok''), while purely semantic retrieval can miss exact command-syntax matches. RRF combines both strengths without requiring score calibration. The tool is invoked lazily---only when the agent encounters a documentation question---so it adds zero tokens to non-documentation conversations.

\subsection{Streaming Protocol}

Responses use OpenAI-style SSE with typed delta fields: \texttt{status\_update}, \texttt{tool\_output}, \texttt{reasoning\_content}, \texttt{content}, \texttt{chart\_artifact}, \texttt{todo\_update}, and \texttt{pending\_actions}. Chart artifacts are filtered from future LLM context to prevent token pollution.

\subsection{Session Management}

Each chat ID maps to a persistent session (conversation memory, pending actions, chart context, runtime config). Evaluation runs use deterministic isolated session IDs for reproducibility. Context budget is managed by separating large artifacts from model input.
