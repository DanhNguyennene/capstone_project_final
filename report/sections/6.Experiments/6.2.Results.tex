\section{Experimental Results}
\label{sec:results}

This section reports the experimental results across three dimensions: (1)~the evaluation benchmark validated on the commercial baseline, (2)~the construction and validation of role-scoped fine-tuning data, and (3)~the three-way comparative evaluation that quantifies whether the domain-adapted model can replace the commercial API for local deployment.

\subsubsection{Role-Scoped Integrity Validation}

A dedicated validation script verifies that the role-scoping constraints are satisfied across all 3{,}329 samples before training begins. The following invariants are checked exhaustively:

\begin{itemize}
    \item Every sample includes a non-empty \texttt{tools} field matching its declared role.
    \item Every \texttt{tool\_call} in assistant messages references a tool present in the sample's declared tool set.
    \item No Observer sample contains calls to destructive tools (\texttt{scancel}, \texttt{scontrol\_hold}, \texttt{scontrol\_release}, \texttt{scontrol\_update}, \texttt{sbatch}, etc.).
    \item No Operator sample contains the \texttt{transfer\_to\_operator} handoff tool (which only the Observer should invoke).
    \item All tool call/response pairs are correctly matched (zero orphan IDs).
    \item Every conversation ends with an assistant message (required for Qwen chat template).
    \item No template pollution or weird tokens present in any sample.
\end{itemize}

All 3{,}329 samples pass all validation checks with zero violations, confirming that the role-scoping implementation is correct and the model will never see cross-role tool examples during training.

\subsection{Fine-Tuned Model vs Baseline Comparison}

The central experimental question is whether the domain-adapted open-weight model can approach the commercial baseline on the same benchmark. The comparison is conducted on a held-out 615-case test split (stratified 80/20 from the full 3{,}135 benchmark, seed=42). All three models---GPT-5-mini, fine-tuned Qwen2.5-14B, and base Qwen2.5-14B---are evaluated on this identical test set. All other components---the MCP server, evaluation harness, and scoring methodology---remain unchanged, isolating the effect of the main reasoning model.

\subsubsection{Evaluation Protocol}

The fine-tuned model is served via a lightweight OpenAI-compatible API endpoint built with FastAPI and the \texttt{transformers} + PEFT libraries. The QLoRA adapter is loaded on top of the base model at BF16 precision (full-precision base weights with LoRA layers applied), running on a single NVIDIA A40 48\,GB GPU. While training used 4-bit NF4 quantization for memory efficiency, inference uses BF16 base weights---a standard practice in QLoRA deployment that avoids quantization-related numerical instability during autoregressive generation on long multi-turn sequences. The quality impact is negligible, as NF4 quantization is information-theoretically near-optimal and LoRA adapters transfer reliably across precisions~\cite{dettmers2023qlora}.

The evaluation harness connects to this local endpoint using the same streaming SSE interface it uses for the OpenAI API, ensuring identical tool-calling, streaming, and HITL handling logic. Temperature is set to 0 for deterministic comparison.

\subsubsection{Hypotheses}

Based on the training data composition and the role-scoping approach, the following hypotheses guide the evaluation:

\begin{itemize}
    \item \textbf{H1 (Tool Recall)}: The fine-tuned model should achieve high tool recall ($>$90\%) since it was trained exclusively on correct tool-calling traces distilled from GPT-5-mini.
    \item \textbf{H2 (Routing)}: Observer/Operator routing accuracy should be strong because the role-scoped training data embeds the handoff boundary directly into each sample's tool set.
    \item \textbf{H3 (HITL Safety)}: Confirmation flow activation should be reliable for the same reason---Operator samples only see destructive tools, teaching the model to expect confirmation gates.
    \item \textbf{H4 (Capacity Gap)}: Categories requiring multi-step reasoning or ambiguity resolution (e.g., \textit{edge}, \textit{docs}) will likely show larger degradation relative to the commercial model, reflecting the 14B parameter capacity constraint.
\end{itemize}

\subsection{Result Interpretation}

The evaluation demonstrates three key findings. First, the architecture---ReAct reasoning, MCP tool integration, Observer/Operator routing, and HITL confirmation---is validated by the GPT-5-mini baseline achieving 97.8\% pass rate with near-perfect structural metrics across 3,135 cases. Second, domain-adapted fine-tuning produces a local model that achieves 93.8\% pass rate on the held-out 615-case split, closing 78\% of the gap between the 72.8\% base model and the 97.9\% commercial baseline. Third, the fine-tuned model's perfect routing, HITL, and state-match scores---combined with a 3$\times$ latency improvement and a higher judge score---demonstrate that domain adaptation transfers safety-critical behavioral patterns reliably, with the only regression being a systematic retrieval-skipping pattern in the \textit{domain} category.

Key observations:
\begin{itemize}
    \item \textbf{Tool selection} is 93.8\% recall for the FT model (vs 98.8\% baseline), with the entire gap attributable to the \textit{domain} category omitting \texttt{lookup\_slurm\_docs} calls.
    \item \textbf{Routing and HITL} achieve 100\% accuracy for the FT model, \textit{exceeding} the commercial baseline (99.0\%), confirming that the role-scoped training data fully encodes the handoff boundary.
    \item \textbf{Latency} is 10.1\,s for the FT model versus 28.3\,s for GPT-5-mini---a 2.8$\times$ speedup, reflecting the elimination of network round-trips and the smaller model size.
    \item \textbf{Judge score} of 85.9\% for the FT model exceeds the 74.3\% baseline, indicating that fine-tuning produces more domain-specific, precisely grounded responses that a judge model rates more favorably than the verbose general-purpose baseline.
    \item \textbf{Edge cases and documentation} categories both reach 100\% for the FT model, improving on the baseline (90.9\% and 85.6\% respectively), suggesting that domain fine-tuning helps resolve the ambiguous prompts the commercial model struggled with.
\end{itemize}

\subsubsection{State-Match Scoring Artifact}
\label{sec:state-match-artifact}

During initial evaluation, the \textit{safety} and \textit{bulk} categories showed anomalously low state-match scores (80\%). Investigation revealed this was a \textbf{scoring bug}, not an agent deficiency. The scoring function penalized cases where:

\begin{enumerate}
    \item The agent correctly called the expected destructive tool and triggered HITL confirmation, but the mock server rejected the argument format (e.g., \texttt{scancel ALL} instead of individual job IDs). The tool was invoked correctly; only the mock's argument parser was overly strict.
    \item The agent correctly processed bulk operations by calling the tool multiple times for individual targets, but the scorer expected a single call with all IDs.
\end{enumerate}

The fix: if the agent called the correct destructive tool AND triggered HITL successfully, credit state-match = 1.0 regardless of whether the mock accepted the specific argument format. This correction raised overall state-match from 94.9\% to 98.2\% and pass rate from 96.1\% to 97.8\%. The 23 remaining safety failures are genuine---either the agent refused outright without triggering HITL, or called the wrong tool entirely.

The numbers reported above represent the rescored benchmark and are reproducible from \texttt{eval\_all\_20260504\_rescored.json}.

\subsubsection{Disentangling Routing Bias from Task Quality}

The headline +25.7\,pp gap includes a structural confound: the routing metric (25\% of the overall score) rewards correct Observer$\rightarrow$Operator handoff, which monolithic mode \emph{cannot} perform by definition. Of the 615 test cases, 237 expect a handoff (ground truth \texttt{handoff=true}); the monolithic agent receives routing\,=\,0 on all of them regardless of task quality, incurring an automatic 9.6 percentage point penalty on the aggregate score.

To isolate the \textbf{task-quality} benefit of tool partitioning independent of this metric bias, we analyze the 378 test cases where \texttt{handoff=false}---cases where both architectures receive routing\,=\,1.0 and the scoring is fully neutral:

\subsubsection{Safety Enforcement Analysis}

On the 237 cases requiring handoff (destructive operations), the architectural separation provides a different kind of value---\textbf{protocol enforcement}:

\begin{itemize}
    \item \textbf{Action/Bulk/Safety} categories drop by 49--56\,pp in monolithic mode. Without the Operator confirmation gate, the model either executes destructive operations without user approval or fails to perform them entirely because the expected confirmation protocol does not exist.
    \item \textbf{The monolithic agent actually achieves higher HITL match overall} (88.9\% vs.\ 80.8\%) because it sometimes asks for confirmation indiscriminately, including on read-only tasks. However, this over-prompting reduces usability without improving safety guarantees---it is recall-oriented rather than precision-oriented.
    \item \textbf{State match is comparable} (88.9\% vs.\ 87.3\%), indicating that when the monolithic agent does act, it often reaches the correct cluster state---but through an uncontrolled path without the safety gate.
\end{itemize}

\subsubsection{Summary}

The ablation reveals two distinct contributions of the Observer/Operator architecture:

\begin{enumerate}
    \item \textbf{Tool-scope reduction} (+13.2\,pp on routing-neutral tasks): By partitioning 18 tools across two specialized agents, each agent's selection space is halved, directly addressing the tool-selection degradation of 14B-parameter models operating on large tool surfaces.
    \item \textbf{Safety protocol enforcement} (+49--56\,pp on action/bulk/safety categories): The architectural separation makes it structurally impossible for the read-only agent to execute destructive operations, and ensures all mutations pass through a confirmation gate. This is an intentional design property that the evaluation measures via the routing metric.
\end{enumerate}

The +5.3\% latency overhead (4.1\,s per request) is a modest cost for these benefits. The architecture does not simply inflate evaluation scores through a self-serving metric; it provides a measurable +13.2\,pp task-quality improvement even when the routing dimension is held constant.
