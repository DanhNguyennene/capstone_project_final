\section{Challenges and Solutions}
\label{sec:challenges}

The development of an LLM-based agent for Slurm cluster management presents several technical and architectural challenges. This section identifies these challenges and outlines the approaches adopted to address them.

\subsection{Challenge 1: Bridging Natural Language to System Commands}

\textbf{Challenge Description:} Slurm operations require precise command syntax with specific parameters and flags. Natural language queries are inherently ambiguous and may not provide all necessary information for command execution. The system must accurately interpret user intent and request clarification when required, while avoiding incorrect command execution that could impact cluster operations.

\textbf{Solution Approach:} We employ a ReAct (Reasoning and Acting) architecture \cite{yao2022react} where the main agent follows a Think $\rightarrow$ Act $\rightarrow$ Observe loop. The MCP server exposes Slurm commands as tools with well-defined Pydantic parameter schemas, enabling the LLM to understand required and optional parameters. The agent reasons about each query before acting, and can engage in multi-turn dialogue using SQLite-backed conversation history to gather missing information from users.

\subsection{Challenge 2: Managing Complex Multi-Step Operations}

\textbf{Challenge Description:} Many cluster management tasks require multiple sequential operations with dependencies between steps. For example, analyzing job performance may require first retrieving job information, then querying accounting data, and finally generating a visualization. Managing these workflows while maintaining coherent conversation context presents significant complexity.

\textbf{Solution Approach:} We implement a multi-agent architecture where the main ReAct agent orchestrates specialized sub-agents invoked as tools. An Analysis Sub-Agent handles read-only queries (cluster status, job information, web search), while an Action Sub-Agent manages job operations. Sub-agents return results to the main agent, which maintains overall context and coordinates execution. A ChartFilteredSession wrapper strips Mermaid chart code from conversation history before sending to the LLM, reducing token consumption since visualization code is verbose but not needed for reasoning.

\subsection{Challenge 3: Real-Time Response Delivery}

\textbf{Challenge Description:} LLM inference and Slurm command execution can introduce noticeable latency, potentially leading to poor user experience. Users may perceive the system as unresponsive during processing, particularly for complex queries that require multiple tool invocations or lengthy computations.

\textbf{Solution Approach:} We implement Server-Sent Events (SSE) for real-time streaming of partial responses in OpenWebUI-compatible format. The backend generates SSE chunks containing incremental content, and the frontend displays updates as the agent generates responses. Chart artifacts are streamed separately and appended at stream end, enabling inline rendering within the conversation interface.

\subsection{Challenge 4: Secure Tool Execution}

\textbf{Challenge Description:} The system must execute Slurm commands on behalf of users, raising concerns about command injection, unauthorized operations, and potential system impact. Improper handling could allow malicious queries to execute harmful commands on the cluster.

\textbf{Solution Approach:} The system implements a layered security model. First, tools are categorized into safe read-only operations (squeue, sinfo, sacct) and dangerous write operations (scancel, sbatch, scontrol updates). Safe tools execute immediately, while dangerous tools are queued in a persistent Pending Actions Store requiring explicit user confirmation. The MCP server uses parameterized tool interfaces with Pydantic validation that prevent arbitrary command injection. Dynamic tool filters ensure sub-agents can only access their permitted tool sets.

\subsection{Challenge 5: Visualization Generation and Delivery}

\textbf{Challenge Description:} Generating and delivering data visualizations within a conversational interface presents unique challenges. The system must determine appropriate chart types based on data characteristics, generate visualizations dynamically, and deliver them through the SSE response stream in a format consumable by the web frontend.

\textbf{Solution Approach:} A dedicated chart generation tool handles visualization using Mermaid diagram syntax. The main agent calls the \texttt{generate\_chart} tool via the MCP server, which returns Mermaid code for chart types including pie charts, bar charts, and flowcharts. Chart artifacts are stored in a context object during the run and transmitted through the SSE stream as Mermaid code blocks. The frontend renders these using a Mermaid renderer, providing inline visualization within the conversation. Critically, a ChartFilteredSession wrapper makes the agent ``blind'' to chart artifacts---Mermaid blocks are stripped from conversation history before LLM inference, significantly reducing token consumption since chart code can be hundreds of tokens that provide no reasoning value.
