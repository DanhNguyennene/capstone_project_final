\section{Natural Language to Structured Operations}
\label{sec:text-to-sql}

Text-to-SQL is the task of translating natural language questions into executable SQL queries over a given database schema. Although the Slurm Agent does not expose SQL to users, Text-to-SQL provides a useful analogy for this project: both problems convert informal language into constrained, executable operations over a structured environment. In Text-to-SQL, the structured environment is a database schema; in the Slurm Agent, it is the MCP tool schema, the Slurm command surface, the current cluster state, and the safety policy attached to each action. The same underlying principles appear in this thesis as structured grounding against explicit tool schemas, constrained action generation, execution-time validation, and human-in-the-loop confirmation for operations that may affect cluster state.

This analogy helps clarify why a Slurm assistant cannot be evaluated only as a chatbot. The system must map user intent to the correct operation, ground that operation in available tools, verify that the operation is safe for the current state, and produce a response that is consistent with actual execution results.

\subsection{Problem Formulation}

Given a user question $q$ and structured context $S$, a grounded semantic parser predicts an executable operation $y$:

\begin{equation}
\hat{y} = \arg\max_y P(y \mid q, S)
\end{equation}

Unlike free-form text generation, valid output must satisfy structural constraints. In a database setting, those constraints include SQL grammar and schema validity. In this project, they include tool availability, tool parameters, cluster state, handoff policy, and human-in-the-loop requirements.

\subsection{Typical Grounded Operation Pipeline}

A practical natural-language-to-operation pipeline usually contains four steps:

\begin{itemize}
    \item \textbf{Schema linking}: map question mentions such as ``running jobs'', ``GPU partition'', ``QoS limit'', or ``pending reason'' to available Slurm tools and fields.
    \item \textbf{Intent and operator inference}: determine whether the user wants monitoring, diagnosis, documentation, submission, job control, or administrative action.
    \item \textbf{Constrained operation selection}: select tools under tool-schema, state, and safety constraints.
    \item \textbf{Execution validation}: run the tool or queue a pending action, then check whether observed behavior matches the expected state and response evidence.
\end{itemize}

Modern structured-operation systems improve reliability by making the schema explicit, narrowing allowed actions, and validating outputs against execution evidence \cite{wang2020ratsql}. These ideas are reused in the Slurm Agent through tool-schema grounding, routing constraints, and confirmation boundaries rather than through SQL generation.



\subsection{Core Challenges}

Grounded operation generation remains difficult due to:

\begin{itemize}
    \item \textbf{Ambiguity}: natural language can under-specify filters or aggregation intent.
    \item \textbf{Schema scale}: broad tool surfaces increase linking and tool-selection complexity.
    \item \textbf{Compositional requests}: multi-step logic, conditional actions, and mixed read/write workflows are error-prone.
    \item \textbf{Execution risk}: a syntactically valid operation may still be unsafe or semantically wrong for the current cluster state.
\end{itemize}

For this reason, evaluation should combine operation-level metrics with execution-based correctness. This motivates the tool recall, routing, HITL, and state-transition metrics used later in the thesis.
